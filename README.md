# TryHackMe — Support

## Introduction

**Support** is a TryHackMe web exploitation room focused on authentication weaknesses, session manipulation, Local File Inclusion, sensitive information disclosure, IDOR, privilege escalation, and command injection.

The objective was to investigate the Support Operations web application, obtain administrative access, and retrieve the available flags.

### Tools Used

* Burp Suite
* ffuf
* CrackStation
* Browser / Developer Tools

---

# 1. Password Discovery

I started by testing the login functionality using **ffuf** and the `rockyou.txt` wordlist.

The password field was replaced with `FUZZ`, allowing ffuf to test each password from the wordlist.

```bash
ffuf -w /usr/share/wordlists/rockyou.txt \
-X POST \
-H "Content-Type: application/x-www-form-urlencoded" \
-d "email=help@support.thm&password=FUZZ" \
-u http://TARGET/
```

The scan returned a valid password:

```text
snoopy
```

<img src="./01%20ffuf%20password.png" alt="FFUF password discovery">

### Problem

The authentication endpoint did not implement an effective **rate-limiting or account lockout mechanism**.

As a result, an attacker could send a very large number of login attempts without being blocked or significantly slowed down.

This made online password brute-forcing practical.

### Exploitation

Because the endpoint accepted repeated authentication attempts, I used **ffuf** with `rockyou.txt` to automate password guessing.

The successful credential discovered was:

```text
Email: help@support.thm
Password: snoopy
```

Using these credentials, I was able to authenticate to the Support Dashboard.

### Solution

The application should implement protections against automated authentication attacks, including:

* Rate limiting based on IP address, account, and session.
* Temporary account lockout or progressive delays after repeated failures.
* CAPTCHA or other bot detection mechanisms where appropriate.
* Monitoring and alerting for abnormal authentication activity.
* Strong password policies and preferably multi-factor authentication.

# 2. Support Dashboard

After logging in, I reached the Support Dashboard.

<img src="./02%20dashboard.png" alt="Support Dashboard">

The dashboard contained several interesting functionalities, so I started intercepting requests using **Burp Suite**.

### Problem

The dashboard exposed multiple application features that could be interacted with through HTTP requests.

Because the application relied heavily on server-side functionality and cookies for access control, intercepting and modifying those requests provided an opportunity to test whether authorization was properly enforced.

### Exploitation

I used Burp Suite to inspect requests, cookies, parameters, and responses generated by the dashboard.

This allowed me to identify security-sensitive values that were being sent by the client.

### Solution

Sensitive authorization decisions should never rely solely on values supplied by the browser.

The server should independently verify:

* The user's identity.
* The user's role.
* The user's permissions.
* Whether the user is authorized to perform the requested action.

# 3. MD5 Hash Analysis

While inspecting the application's cookies, I found the `isITUser` value.

The value appeared to be an MD5 hash.

I tested possible plaintext values against the hash.

For example, the MD5 representation of:

```text
false
```

was:

```text
68934a3e9455fa72420237eb05902327
```

<img src="./03%20crackstation%20false.png" alt="CrackStation false MD5">

I then tested:

```text
true
```

which produced:

```text
b326b5062b2f0e69046810717534cb09
```

<img src="./04%20crackstation%20true.png" alt="CrackStation true MD5">

This showed that the application was using predictable MD5 values for an authorization-related cookie.

### Problem

The application used a predictable cryptographic representation of a security-sensitive Boolean value:

```text
false → 68934a3e9455fa72420237eb05902327
true  → b326b5062b2f0e69046810717534cb09
```

MD5 is not suitable for security-sensitive cryptographic purposes.

More importantly, however, the main vulnerability was not simply the use of MD5. The critical problem was that the resulting value was stored in a **client-controlled cookie and used in an authorization decision**.

### Exploitation

By identifying that the hash represented the value `true`, I was able to reproduce the expected value and manipulate the authorization cookie.

### Solution

The application should:

* Never use MD5 for security-sensitive operations.
* Never store authorization state directly in a client-controlled cookie.
* Store roles and permissions server-side.
* Use a secure, signed session mechanism.
* Recalculate authorization from trusted server-side data for every protected request.

# 4. Cookie Analysis

Using Burp Suite, I inspected the original request.

The cookie contained:

```http
Cookie: PHPSESSID=<session>;
isITUser=b326b5062b2f0e69046810717534cb09
```

<img src="./05%20burp%20original%20cookie%20.png" alt="Original isITUser cookie">

### Problem

The `isITUser` cookie represented a security-sensitive authorization state.

Because cookies are controlled by the client, an attacker could modify the value before sending the request back to the server.

This is a **client-side authorization flaw**.

### Exploitation

I identified that the application expected the MD5 representation of `true` for the `isITUser` value.

I could therefore replace the cookie with:

```text
b326b5062b2f0e69046810717534cb09
```

and test whether the server would accept the modified authorization state.

### Solution

Authorization must be performed using trusted server-side information.

For example:

```text
Session ID
    ↓
Server-side session
    ↓
User record
    ↓
Role / permissions
    ↓
Authorization decision
```

The server should not make privileged decisions based on a Boolean or hash supplied directly by the browser.

# 5. Cookie Manipulation

I replaced the `isITUser` cookie value with the MD5 hash corresponding to `true`.

```http
Cookie: PHPSESSID=<session>;
isITUser=b326b5062b2f0e69046810717534cb09
```

<img src="./06%20cookie%20swap%20burp.png" alt="Cookie manipulation with Burp Suite">

After modifying the cookie, the application treated the user as an IT user.

### Problem

The application trusted the value supplied by the client to determine whether the authenticated user had additional privileges.

This bypassed the intended authorization mechanism.

### Exploitation

By modifying:

```text
isITUser=false
```

into the value corresponding to:

```text
isITUser=true
```

I obtained access to functionality intended for IT users.

### Solution

The server should determine the user's privileges from trusted server-side data.

A secure implementation would resemble:

```php
$user = getUserFromSession($_SESSION['user_id']);

if ($user['role'] !== 'IT') {
    denyAccess();
}
```

rather than trusting:

```php
$_COOKIE['isITUser']
```

for authorization.

# 6. Local File Inclusion

While exploring the dashboard, I discovered the `skin` parameter.

I tested:

```text
/dashboard.php?skin=.config
```

<img src="./07%20lfi%20skin%20attempt.png" alt="LFI skin parameter attempt">

The application processed the supplied value, suggesting that server-side resources were being loaded.

I then inspected the resulting source.

### Problem

The application used user-controlled input to determine which server-side resource should be loaded.

Insufficient validation of file paths can lead to **Local File Inclusion (LFI)** and potentially expose local application files.

### Exploitation

I manipulated the `skin` parameter and observed that server-side resources could be loaded and returned to the client.

This allowed me to access application source code that should never have been exposed.

### Solution

The application should:

* Use a strict allowlist of permitted themes/files.
* Never concatenate raw user input into filesystem paths.
* Resolve and validate paths before loading them.
* Store themes using fixed identifiers rather than arbitrary filenames.

For example:

```php
$allowed = [
    'default' => 'skins/default.php',
    'red'     => 'skins/red.php',
    'green'   => 'skins/green.php',
    'blue'    => 'skins/blue.php'
];
```

# 7. Source Code Disclosure

Viewing the resulting source revealed server-side PHP code that should not have been exposed to the browser.

<img src="./08%20lfi%20config%20source.png" alt="LFI source code disclosure">

The source contained sensitive configuration values:

```php
$MASTER_PASSWORD = 'support@110';
$SITE_VER = '1.0';
$SITE_NAME = 'support_portal';
```

### Problem

The application exposed **server-side PHP source code** through a web-accessible endpoint.

This resulted in disclosure of:

* Application configuration.
* Internal variables.
* Credentials.
* Version information.
* Application structure.

The exposed master password was particularly sensitive.

### Exploitation

By abusing the file inclusion functionality, I was able to retrieve the application's PHP source and recover:

```text
$MASTER_PASSWORD = 'support@110';
```

This credential could then be used during subsequent authentication testing.

### Solution

The application should:

* Prevent arbitrary file inclusion.
* Keep configuration files outside the web root where possible.
* Never hard-code passwords in source code.
* Store secrets in environment variables or a secret manager.
* Disable direct access to sensitive files.
* Ensure PHP source code is executed server-side rather than returned as plaintext.

# 8. IDOR / API Enumeration

I then investigated the application's internal API.

The endpoint:

```text
/user/1
```

returned information about the user.

<img src="./09%20idor%20user%20api.png" alt="IDOR user API">

The response included:

```json
{
    "email": "specialadmin@support.thm",
    "2FA": false,
    "admin": true
}
```

### Problem

The API exposed user information based on a user-controlled object identifier.

The server did not sufficiently verify whether the authenticated user was authorized to access the requested user object.

This is a **Broken Object-Level Authorization (BOLA)** / **IDOR** vulnerability.

### Exploitation

I modified the user identifier in the API request:

```text
/user/1
```

and was able to retrieve information belonging to another account.

The response revealed:

```text
email: specialadmin@support.thm
admin: true
```

This exposed a privileged account.

### Solution

Every object access must verify ownership or authorization.

For example:

```php
$user = getUser($_GET['id']);

if ($user['id'] !== $_SESSION['user_id'] && !isAdmin()) {
    http_response_code(403);
    exit;
}
```

Object identifiers should never be treated as authorization.

I attempted to authenticate using the discovered administrator account.

The first attempt failed.

<img src="./10%20invalid%20creds.png" alt="Invalid administrator credentials">

After correlating the information discovered during the previous stages, I was able to authenticate successfully without `@`.

### Problem

The application exposed information through several previous vulnerabilities that could be combined to recover or infer authentication data.

The individual weaknesses therefore created a larger attack chain.

### Exploitation

The previously disclosed information was correlated with the administrator account discovered through API enumeration.

This allowed successful authentication to the privileged account.

### Solution

Sensitive authentication information should never be exposed through:

* Client-side parameters.
* Source code.
* API responses.
* Debug information.
* Weak authorization mechanisms.

Administrator accounts should also use:

* Strong unique passwords.
* Multi-factor authentication.
* Account monitoring.
* Proper access controls.
* Secure password storage.

The application confirmed successful administrator authentication.

<img src="./11%20admin%20confirmed%20flag%20.png" alt="Administrator access confirmed">

The page displayed the administrator flag:


### Problem

The combined weaknesses allowed a low-privileged user to obtain an administrator account.

This represents a complete **privilege escalation** chain.

### Exploitation

The attack chain was:

```text
Weak authentication protection
        ↓
Cookie authorization bypass
        ↓
Source code disclosure
        ↓
Credential discovery
        ↓
IDOR / API enumeration
        ↓
Administrator account discovery
        ↓
Administrator authentication
```

### Solution

The application should enforce defense in depth:

* Strong authentication.
* Server-side authorization.
* Secure session management.
* Proper API authorization.
* Protection of sensitive source/configuration files.
* Least-privilege access controls.
* MFA for administrator accounts.

# 11. Command Injection

After obtaining administrator privileges, I investigated the system functionality available through the dashboard.

I discovered a parameter named:

```text
sys
```

The application passed the supplied value to a system command without properly separating trusted commands from user-controlled input.

I injected an additional command:

```text
sys=date;cat /home/ubuntu/user.txt
```

<img src="./12%20cmd%20injection%20flag%20.png" alt="Command injection and user flag">

The injected command was executed successfully and returned the contents of the user flag.

### Problem

The application passed attacker-controlled input to an operating system command.

This created a **Command Injection** vulnerability.

The intended input was a legitimate `date` command, but the application failed to safely constrain what was executed.

### Exploitation

The original application functionality executed:

```text
date
```

I modified the parameter to append another command:

```text
date;cat /home/ubuntu/user.txt
```

Because the shell interpreted `;` as a command separator, the second command was executed.

### Solution

The safest solution is **not to invoke a shell with user-controlled input**.

Instead of:

```php
system("date " . $_POST['sys']);
```

the application should use a fixed command or a strict allowlist.

For example:

```php
$allowed = [
    'date' => 'date',
    'time' => 'date +"%H:%M:%S"'
];

$option = $_POST['sys'] ?? 'date';

if (!isset($allowed[$option])) {
    exit('Invalid option');
}

echo shell_exec($allowed[$option]);
```

Even better, if the required output can be generated directly in PHP, the operating system command should not be used at all.

# 12. User Flag

The final flag obtained through command injection was:

```text
THM{GOT_THE_FLAG001}
```

### Result

This demonstrated successful operating-system command execution on the target machine.

### Security Impact

Command injection can potentially allow an attacker to:

* Read sensitive files.
* Access credentials.
* Execute arbitrary commands.
* Modify application data.
* Establish persistence.
* Compromise the underlying operating system.

### Solution

Avoid shell execution whenever possible.

If system commands are unavoidable:

* Use fixed commands.
* Use strict allowlists.
* Avoid concatenating user input.
* Avoid shell interpreters.
* Validate input on the server.
* Run the application with minimal OS privileges.

# Vulnerabilities Identified

### 1. Missing Rate Limiting

The login endpoint allowed repeated authentication attempts, making password brute-forcing practical.

**Impact:** Increased risk of credential guessing and account compromise.

**Solution:** Rate limiting, progressive delays, lockout mechanisms, monitoring, and MFA.

---

### 2. Client-Side Authorization

The application trusted the `isITUser` cookie to determine authorization state.

**Impact:** An attacker could manipulate the cookie and gain access to privileged functionality.

**Solution:** Perform authorization entirely from trusted server-side session and role data.

---

### 3. Weak Cryptographic Practice

MD5 was used to represent a security-sensitive authorization value.

**Impact:** Predictable values could be trivially reproduced.

**Solution:** Do not use MD5 for security-sensitive purposes and do not expose authorization state to the client.

---

### 4. Local File Inclusion

The `skin` parameter could be abused to access server-side application resources.

**Impact:** Potential disclosure of sensitive files and application source code.

**Solution:** Strict allowlisting and secure server-side file resolution.

---

### 5. Sensitive Information Disclosure

Server-side PHP source code exposed credentials and application configuration.

**Impact:** Credential compromise and increased attack surface.

**Solution:** Prevent source disclosure, protect configuration files, and store secrets securely.

---

### 6. IDOR / BOLA

The API allowed access to user objects through predictable identifiers without sufficient authorization checks.

**Impact:** Exposure of other users' information, including privileged accounts.

**Solution:** Enforce object-level authorization on every API request.

---

### 7. Privilege Escalation

The combination of authorization weaknesses, source disclosure, and API enumeration allowed a low-privileged user to reach administrator access.

**Impact:** Unauthorized administrative access.

**Solution:** Enforce least privilege and independently validate all authorization decisions.

---

### 8. Command Injection

The `sys` parameter allowed additional operating system commands to be executed.

**Impact:** Arbitrary command execution on the target server.

**Solution:** Avoid shell execution and use strict allowlists and safe APIs.

---

# Key Takeaways

This room demonstrated how several individually significant weaknesses can be chained into a complete compromise.

The main lessons were:

* **Authentication must be protected against brute-force attacks.**
* **Rate limiting is essential for login endpoints.**
* **Never trust client-controlled authorization values.**
* **Do not use MD5 for security-sensitive operations.**
* **Validate and allowlist file inclusion parameters.**
* **Never expose server-side source code or credentials.**
* **Every API object requires an authorization check.**
* **Do not pass raw user input to operating system commands.**
* **Security vulnerabilities become significantly more dangerous when they can be chained together.**
* **Burp Suite is extremely useful for understanding and manipulating application behavior.**

---

# Conclusion

The **Support** room provided practical experience with a complete web application attack chain.

Starting with password discovery made possible by the absence of effective rate limiting, I authenticated to the application and analyzed its session and authorization mechanisms.

I identified a client-side authorization weakness in the `isITUser` cookie, discovered an LFI vulnerability that exposed application source code and credentials, and then used API enumeration to identify an administrator account through an IDOR/BOLA vulnerability.

After obtaining administrator access, I exploited a command injection vulnerability to execute operating-system commands and retrieve the final user flag.

The room reinforced an important security principle: **a vulnerable application rarely has only one problem**. Multiple weaknesses can be combined to escalate the impact from a simple authentication weakness to full application and system compromise.
